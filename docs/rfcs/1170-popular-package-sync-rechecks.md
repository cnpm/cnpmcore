# RFC: 热门包的 upstream changes 延迟复查

- 状态：Draft，包含第一阶段实现
- 关联问题：[#1170](https://github.com/cnpm/cnpmcore/issues/1170)

## 问题与证据

npm 在 [2026-07-28 的公告](https://github.blog/changelog/2026-07-28-npm-publish-time-malware-scanning-and-dual-use-metadata/)中引入发布时恶意软件扫描。版本通常需要约五分钟才能安装，高峰期可能需要十五分钟或更长时间。这不是可用时间承诺，扫描期间仍可修改 dist-tag。

[官方讨论](https://github.com/orgs/community/discussions/203413)建议自动化通过轮询或重试确认可用性，不能假定固定等待时间足够。讨论中 Cloudflare 的发布维护者也反馈了 `wrangler` 已可用但其依赖 `miniflare` 仍在扫描的情况。

公告没有承诺 changes 通知与版本可用性的顺序，因此本方案不把通知当作可安装证明。同步任务可能读到旧 manifest，也可能下载新版本 tarball 失败。当前两个同步分支都可能在部分版本失败后结束为成功。没有下一条通知时，镜像可能长期停留在旧版本。

#1170 的两层同步日志均显示 `155 => 155, 0 added`，并执行了缓存清理。这不能证明该次故障由扫描导致，缓存和生成的 manifest 仍需独立排查。本 RFC 解决通知后的有限补偿，不将该事件归因于单一原因。

## 目标与范围

仅为达到使用量阈值的包增加自动复查，降低人工同步需求。额外工作量必须有明确上限。所有包仍保留原有即时同步；不对所有包轮询，不递归展开依赖，不修改发布隔离或封禁策略。

第一阶段通过独立调度器调用现有同步实现，兼容普通 JSON 和 Packument 两个分支。缓存代际、CDN 主动探测、完整依赖树可用性及普通任务的并发合并重构不在本次实现中。

## 进入保障范围的条件

默认关闭 `cnpmcore.syncRecheck.enabled`。开启后，后台计算前七个完整自然日的下载量，使用与现有计数写入一致的服务器时区，汇总包的所有具体版本。排除 `version = '*'` 的历史导入汇总，避免与版本计数重复相加；排除私有包。

满足 `minWeeklyDownloads` 的包按下载量降序进入集合，但总数不超过 `maxPackages`。`include` 指定的包优先占用同一容量，不绕过容量限制。阈值附近的变动在下一次集合刷新时生效。

大规模部署可通过 `popularityUrl` 提供共享快照，替代本地聚合。例如由 npmmirror 的下载统计（含 CDN 日志）生成，再供 npm-facing 的 `r.cnpmjs.org` 使用。上游同步节点的自身请求量不能直接代表用户需求。

快照格式：

```json
{
  "updatedAt": "2026-10-17T00:00:00.000Z",
  "packages": [
    { "name": "eslint-plugin-oxlint", "downloads": 20000 },
    { "name": "oxlint", "downloads": 30000 }
  ]
}
```

数值仅为格式示例，不是这些包的真实统计。快照必须在最近二十四小时内生成。刷新失败保留上次集合至其 TTL 到期，不阻断正常同步。每条 changes 只检查 Redis 集合，不查询下载表或外部统计 API。后台调度每分钟检查是否需要刷新，因此启动后首次集合建立可能需要一分钟。

本地聚合按月份筛选、在数据库中汇总并限制返回数量。启用前应检查大规模数据库的查询耗时；推荐大型镜像使用已有统计系统生成的共享快照。

## 调度与容量

```typescript
cnpmcore: {
  syncRecheck: {
    enabled: false,
    minWeeklyDownloads: 10_000,
    maxPackages: 2000,
    include: [],
    popularityUrl: '',
    refreshInterval: 60 * 60_000,
    delays: [2 * 60_000, 10 * 60_000, 30 * 60_000],
    maxAttemptsPerHour: 3,
    dispatchInterval: 1000,
  },
}
```

这些是可调整的起始值，不是生产流量分析所得的最优值。生产上线前统计阈值覆盖的包数及其 changes 频率。

1. 正常同步任务建立后，仅为集合内的包记录复查意图。
2. 每个 `(registryId, fullname)` 最多一条待处理记录；全局待处理记录也不超过 `maxPackages`。
3. 默认最早在首次通知后的第 2、10、30 分钟复查，队列拥塞时顺延。后续通知合并到同一记录，不不断推迟到期时间，不清空重试预算。
4. 每个包与源在任意滚动一小时内最多预留三次额外同步。记录结束后仍保留预算，下一条通知不能重置它。额度不足时等待最早的额度释放。
5. 所有节点共享调度限速，默认每秒最多处理一条到期记录。现有同步队列达到高水位时停止派发；实际同步仍受已有 worker 并发限制。
6. 包已有排队或执行中的任务时，延后检查，避免把补偿合并进已经读取旧快照的任务。
7. 额外任务设置 `maxAttempts: 1`，网络或依赖校验失败后不进入原有的即时重试循环。底层 HTTP 客户端的有限请求重试保持原行为。

容量不足时不增加补偿记录，正常同步仍执行。因此这里的“保障”是有预算的尽力补偿，不能承诺 npm 任意扫描时长下的绝对可用时间。

## 完成条件

cnpm changes 的 `PACKAGE_VERSION_ADDED` 保留目标版本。最近一次同步成功、没有任务错误且所有目标版本出现在本地 full manifest 时，可提前结束。tag 或其他元数据事件没有足够的目标信息，按未知目标处理。

npm changes 不提供可靠的目标版本；即使同步返回成功或 `0 added`，仍保留有限复查。复查次数用尽后停止，后续新通知仍受滚动预算限制。此方案不依赖修改两个同步分支的成功判定，也不会无限重试永久不存在的版本。

## 一致性与故障恢复

Redis 保存记录、到期有序集合和滚动预算；Lua 比较并替换同时更新记录和到期项。进程重启不丢失这些状态。记录有执行租约，进程崩溃后可再次领取。预留同步任务 ID 后再入队；重启时同时检查活动任务和历史任务，复用已预留的 ID，避免重新消耗预算。

如果数据库任务已保存但队列写入失败，恢复时重新确保 waiting 任务在普通队列中，不依赖三十分钟的普通超时恢复。

通知更新记录的 generation。派发确认或提前完成不能清除领取后新到达的通知。补偿在 Redis 中的持久性取决于部署的 Redis 持久化及故障恢复配置；Redis 数据丢失后无法从数据库重建所有补偿记录。普通 changes 同步继续运行。需要更强故障恢复保证时，可在后续版本引入数据库 outbox。

changes 游标仅在正常任务和适用的补偿意图保存后前进。暂时性写入失败停止当前批次，后续从已保存游标重放。确定的 registry 不匹配仍可跳过。

普通队列重复 `push` 使用 `ZADD NX`，保留已有位置，避免热门包因多次通知反而移到队尾。

## 验证与上线

覆盖阈值边界、跨月和跨年汇总、导入汇总排除、集合容量、低热度零补偿、重复通知合并、处理中通知、滚动预算、租约恢复、派发 ID 恢复、已同步目标提前结束及无目标旧快照复查。两个同步分支继续使用原测试，并增加补偿调用集成测试。

先启用少量 `include` 包，观察集合数量、补偿派发数量、队列水位及实际新版本同步延迟，再设置生产阈值。调整或关闭开关不影响普通同步。关闭后暂停补偿派发；记录按 TTL 清理。初始观察阶段不增加全量热门包周期扫描。
